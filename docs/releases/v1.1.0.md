Hayat v1.1.0 makes OAuth clients part of services, adds a per-account appearance that every integrated app can read, and reworks the console's roles, services and resource-tree pages. Operators upgrading from v1.0.0 should run migrations; developers integrating apps should check the client and audience changes below.

## Highlights

### OAuth clients belong to services
Every OAuth client now has a `service_id`, and the old `ClientService` RPCs are gone. Clients are managed through `RegistryService` (`ListServiceClients`, `CreateServiceClient`, `UpdateServiceClient`, `RotateServiceClientSecret`, `SetServiceClientDisabled`), so a service's owners manage its own sign-in clients. In the console this is the service page's **Clients → Add sign-in client**. Access tokens now carry the client and its service in `aud`, so a service checking its own namespace accepts any of its sign-in clients.

### Per-account appearance
Each account can set one theme — colors, font, text size, density, corners, sidebar and content width — at Account → Appearance. Services read it with `DirectoryService.GetUserAppearance` and apply it to the person's session rather than storing a copy. Fields left on Default stay each app's own, and an account that never chose a theme returns no appearance.

### Permission labels
Permissions can carry a short human name (`label`) shown wherever admins pick or read permissions; without one the console falls back to the key. Service contracts set it per permission in the manifest, and labels and descriptions are display text that may change between versions.

### Reworked roles pages
Roles are shown in plain words — what a role lets someone do, grouped by service, where it can be granted and who holds it — plus a By service view and a full-page editor that starts from a copy, previews the role live and warns when a permission can't take effect where the role can be granted. `CatalogService.ListRoleGrants` returns where a role is granted across every tenant.

### Nested groups and node access
Groups nest like an org chart: people on a subgroup count as members of the group above it, and `GetNode` now returns them as `subgroup_members` with the groups they came through. The new `TreeAdminService.ListNodeAccess` lists everyone who reaches a node and how (owner, direct grant, group grant, tenant-wide grant or placement), and the console shows one access list per node with a searchable, paged modal.

### Tenant roster paging and member grants
`GetTenant` no longer returns members; use the new paged `TenantService.ListMembers` instead. Services can call `DirectoryService.ListTenantGrants` to see what each member was granted in a tenant — to them, to a group they are on, or to the whole tenant — limited to the tenant, its groups and the calling service's own resource types.

### Fixes and polish
- `RegistryService.UpdateService` changes a service's display name and description; the namespace never changes.
- `ServiceInfo` reports `builtin` (Hayat itself) and `sign_in_clients`.
- Contract versions go live when published; only versions that place types under another service's types wait for that service's owners to approve.
- `hayat import` no longer approves the bundle's contract, and registers the sign-in client under the service.

## Upgrading

Run `hayat migrate`; this release adds migrations 0003–0006 for both Postgres and YugabyteDB. Migration 0004 assigns every existing OAuth client to a service: clients tied to a service's API credential move to that service, and all others go to the platform (`hayat`), where an instance admin manages them. Migration 0005 returns clients that `hayat import` registered as "<display name> (web)" to their service; a service renamed since keeps its client with the platform.

Breaking API changes: `ClientService` and its messages are removed — use the `RegistryService` client RPCs. `GetTenantResponse.members` is removed (field 2 is reserved) — use `ListMembers`. Services verifying access tokens should pass their namespace as the audience.
